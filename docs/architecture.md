# Architecture, content format v1, and save format v2

| Crate | Responsibility |
| --- | --- |
| `luna-model` | Serde content contract, validation, semantic text spans, starter actions |
| `luna-core` | Parser, event dispatch, transactional execution, complete mutable state |
| `luna-project` | Canonical files, disk revisions, recoverable saves, ZIP export/validation |
| `luna-editor` | Authenticated loopback API, embedded UI, project operations, playtest host |
| `luna-runner` | Immutable installations, CLI, player save storage, terminal host |

The React/TypeScript editor uses React Flow for locations and exits and custom Blockly blocks for typed action flows. It never executes game rules in JavaScript. Rust types generate `web/src/contracts.ts`; CI checks that this file has not drifted.

The Actions tab edits command actions and exits, with separate lists and a remembered flow selection per owner. Triggers has a dedicated list and block canvas under Game data, grouped into command, state, and value triggers and filterable by owner. Entity inspectors link to their triggers; trigger selection opens its settings and block flow. Flow roots expose action requirements, trigger conditions, or exit visibility and traversability as Boolean inputs alongside the effects. These inputs and the inspector edit the same canonical conditions. ALL/ANY blocks preserve arbitrary child counts, including empty and single-child groups. Restoring an older workspace adds missing condition inputs from the canonical model without discarding its effect layout. Inspector and playtest collapse controls affect only the editor layout and keep panel contents mounted.

The hierarchy groups Variables, Command vocabulary, Triggers, and Endings under Game data. Variables, vocabulary, and endings select inspector editors and return the canvas to the world map. Triggers opens its block workspace. All entries expand the inspector and preserve the playtest. Page keys are separate from valid entity IDs. The Endings editor owns `game.endings` and `game.require_ending`; Game settings links to it. Ending edits retain stable IDs and the existing outcome/message model, so END GAME references, exports, and player saves use the same contract.

### Warning acknowledgements

Warnings carry an optional `warning_key`, a SHA-256 fingerprint of the versioned rule, subject, field, message, and relevant cause. Overlap keys include the conflicting vocabulary phrase or flow matching settings; unreachable-room/ending keys include the starting room; movement-cycle keys include the movement graph reachable from that room. Display-name, description, map-layout, and acknowledgement edits do not reset an otherwise unchanged warning.

`editor.warning_acknowledgements` is an optional list of `{warning_key, subject, field, message, reason}` records; an omitted reason defaults to empty. The findings panel provides an acknowledgement dialog and a separate review/restore filter, including changed and resolved records. Active counts and inline/block highlights omit exact acknowledged game warnings. Errors and drafts cannot be acknowledged. Rust validation retains every diagnostic; acknowledgements change only the editor's presentation. Metadata edits use project history and saving without invalidating validation or playtest snapshots. The project retains reasons across reopening and Save As; exports and player saves contain no acknowledgements. Older projects default to no acknowledgements. Content and saved-state versions are unchanged.

## Authoring contract

`game.json` contains game identity, format version, a three-component numeric content version, metadata, initial typed variables, endings, global actions/triggers, and the relative asset list. `vocabulary.json` stores shared verbs, synonyms, and optional semantic interaction events. Locations, objects, and characters have individual JSON files named by immutable IDs. Renaming display text does not rename IDs or references. New content receives UUIDs; imported IDs may also use safe ASCII slugs.

Actions, conditions, and effects are tagged enums defined in `luna-model`. Boolean, signed 32-bit integer, and text values are supported. Custom entity properties have declared initial types. Command patterns combine a verb reference with literal phrases and fixed entity references. No scripts, regular expressions, or executable Blockly code are persisted.

The `print_description` effect stores an `entity` reference and reads that location, object, or character's current authored description when executed. New entities receive an examine action using this effect, including the initial location in a blank project. Starter object actions use the same effect; the editor skips starter commands whose verb and pattern already exist.

`editor/map-layout.json` stores map positions, optional Blockly workspaces, and route layouts keyed by exit ID. A route layout records optional source/target border anchors (side and fractional position) and a label displacement from the route midpoint. Anchors move with their rooms; labels never alter arrow geometry. Older layouts without route data use automatic placement. These fields are editor metadata and remain excluded from exported games. The typed effects remain canonical; workspace restoration must agree with them or the editor rebuilds the blocks. Response-sequence IDs are independent of response order and persist across edits.

Drafts can have semantic validation errors and remain saveable. Export and new playtests require valid content. Runtime restores additionally validate every saved entity, property, visit counter, ending, and response cursor against the immutable game definition.

### Saved block templates

`EditorLayout.templates` is a project-local `Vec<BlockTemplate>`, defaulting to empty for older layouts. Each entry has a stable template ID, name, optional source entity owner, and `TemplateContent`: either a complete `Action` snapshot or an ordered effect chain. A `TemplateEntity` snapshot records each referenced entity's ID, name, kind, and property names; `text_variables` records exact global-variable names used in messages. These snapshots keep replacement choices meaningful after the source is renamed or deleted and preserve variable-versus-property lookup precedence. Templates are editor metadata: unused broken references do not invalidate game logic, and the library is excluded from bundles. Existing project saves, revisions, recovery drafts, and Save As include it. No game-content or player-save format changes are needed; older editors reject the added metadata field rather than silently dropping it.

The canvas library can save whole actions, all effects in a flow, or a selected block and its following chain, including nested branches and sequence follow-ups. An insertion is a deep copy. The editor regenerates the action ID and every contained response-sequence ID, rewrites reset references to contained sequences, and keeps references to external sequences. Entity replacements traverse command patterns, requirements, Boolean groups, nested effects, numeric operands, response text, fallback text, and failed-requirement messages. Typed uses constrain replacement kinds (objects for inventory effects, characters for inventories, locations for movement); generic entity references can cross kinds. The source owner defaults to the target entity when compatible, and other references default to their current entities. `@current` retains its special placement meaning.

Message replacements follow percent escaping and colour-span boundaries, preserve literal pattern phrases and stored text values, and resolve dotted entity IDs against the snapshotted property names. Exact global message variables retain their original meaning even if subsequently deleted; insertion validation then reports the missing dependency. The editor validates the proposed target action/flow and new sequence IDs before inserting, so incompatible properties and other missing dependencies leave the project unchanged and can be corrected in the replacement choices. Appending blocks creates one grouped Blockly operation with full block metadata and preserves existing block IDs/positions; undo/redo restores the authored responses and sequence IDs. Template rename/delete changes only the library; inserted copies are ordinary canonical logic with independent progress and no runtime dependency on the template.

### Character inventories

Every object has one canonical placement: `{"type":"inventory"}` for the player, `{"type":"location","location":"room-id"}` for a room, `{"type":"character","character":"keeper-id"}` for a character, or `{"type":"absent"}`. Character inventory lists are derived from object placements in the editor and runtime; there is no second list to synchronize. Character references must resolve to characters. An existing object must have a non-absent placement, and consumed objects must be absent. Saves and playtest state edits validate these invariants.

`give_character` has `object` and `character` references. Like existing `give` and `place`, it assigns the destination, makes the object exist, and clears consumption. `give` targets the player; `place` targets a room or `@current`. These effects transfer an item from any previous placement and can introduce an absent item. Use requirements to constrain a transfer to a particular source owner. `remove` makes the object absent without consuming it; `consume` makes it absent and consumed. Neither implicitly places an item in its former holder's room.

`character_carrying` has `character` and `object` references. It checks live ownership, existence, and non-consumption independently of the holder's visibility or location. Existing `carrying` continues to mean the player. Held objects are outside player command scope, including examine/take and the `visible` condition, and do not appear in look/inventory listings. An authored action on the character (for example, `talk Keeper`) can check its inventory and transfer an item. Avoid binding a still-held object as a command-pattern entity; reference it from the action's conditions and effects instead.

Moving into player inventory emits Take when ownership changes. Moving from player inventory to a character or room emits Drop after the new placement is set. Reassigning the same character owner or transferring between non-player owners emits neither. Existing remove/consume event behavior is unchanged. All transfers and resulting triggers share command rollback. Character placement references follow the holder's current location without rewriting item placements.

The object inspector's initial placement menu and character inspector's initial inventory edit the same object field. Removing an initial inventory entry with **Place in room** selects the holder's initial location explicitly. The playtest state inspector derives current inventory from saved placements and keeps existence/consumption consistent when changing placement.

Character inventories add a placement variant without changing the content format or adding a separate state inventory list. Old projects, player carrying conditions, and Blockly metadata remain readable. Character inventories require an engine supporting the new variants. Older engines reject unknown content/state variants instead of dropping ownership. Invalid owner references or inconsistent saved placements produce compatibility errors; they are not silently reassigned. Existing game/content identity and fingerprint checks remain in force. See the player persistence section for hint history and current save-format compatibility.

### Character movement and speech

`move_character` stores `character` and `location` references. The destination is a location ID or `@current`, resolved against the player's location at execution time. It changes only the character's live location; hidden state and every held object's canonical placement remain intact. Moving to the same room is a no-op. It does not run player Enter, FirstEnter, Leave, Take, Drop, or Speak events, increment visits, show a room description, or move the player. The enclosing action still emits its normal interaction/Command events. Author additional effects explicitly for arrival or departure behaviour. Player command scope and visibility immediately use the new position. Structural ending validation follows possible character positions without treating character destinations as rooms the player can reach.

`character_says` stores `character` and formatted `text`. It reads the referenced character's current authored name and optional `name_colour`, then emits literal name, uncoloured ` says: `, and the message's formatted spans as one transcript line. The name is never parsed as markup or placeholders. The message uses the same live variable/property expansion and literal insertion rules as SAY. A speech effect does not fire Speak or gate output by speaker visibility; authors can add a visible condition. `text::speech` supplies the shared speaker-prefix formatting for future conversation features.

`Character.name_colour` defaults to null for older content and accepts null or one of the existing 16 semantic colour names. Both new effects validate typed references and formatted messages, participate in nested IF/ELSE and response follow-ups, and share command rollback. The editor provides both blocks, synchronized inspector controls, a character name-colour picker/preview, and typed template replacement for speakers, destinations, and speech placeholders. Renaming a character preserves its references.

Character locations and held-item ownership already live in `GameState`, so content stays in format 1 and player saves in format 2. Restoring a save reinstates positions and ownership without replaying movement, speech, or triggers. Existing projects without a name colour remain readable; older engines reject new effect variants or the new character field rather than silently discarding behaviour. Releasing an edited game still requires the usual content-version and bundle-fingerprint compatibility checks.

### Integer arithmetic

`update_variable` targets a global variable by `name`; `update_property` targets a custom property by `entity` and `name`. Both include `op` (`add`, `subtract`, `multiply`, or `divide`) and a tagged `operand`: `literal` with an integer `value`, `variable` with a `name`, or `property` with an `entity` and `name`. For example:

```json
{"type":"update_variable","name":"chances","op":"subtract","operand":{"type":"literal","value":1}}
```

The target and any referenced operand must have integer schemas. Literal zero divisors are validation errors; referenced divisors may start at zero and are checked against live state at execution. Each effect computes `target = current target OP current operand`, reading both before writing. Earlier effects are visible, including when an operand references the target itself. Calculations use checked signed 32-bit operations; division truncates toward zero. Zero division and overflow (including −2,147,483,648 divided by −1) fail the transaction and discard all its state and output.

Blockly numeric inputs accept only Number outputs. The Values category supplies literal, variable, and property blocks; update blocks start with a literal shadow of 1, restored when a connected reference is removed. Dropdowns filter to integer schemas while preserving incompatible or missing references for diagnostics. Saved workspaces round trip these inputs through the canonical effects. Existing literal SET effects and Boolean condition inputs retain their behavior. No nested math expressions are supported.

Arithmetic adds no state fields and requires no format migration. Existing projects and workspaces remain readable; arithmetic effects require an engine supporting them. Older engines reject the unknown effect rather than dropping it. Existing game identity, content-version, fingerprint, and state-schema compatibility checks still apply.

## Parser and execution

Normalization lowercases Unicode characters, treats punctuation as word separators, and collapses whitespace. Multiword vocabulary and aliases match complete token sequences. `game.ignored_words` lists optional single-word prefixes before entity references and implicit route names; omitted lists default to `a`, `an`, `the`, while an explicit empty list disables this behavior. The matcher may skip leading prefix words at each entity boundary and strips them from the start of authored names/aliases, while preserving nonempty names made entirely of prefix words. It preserves words inside names, literal pattern parts, verbs, and host-control arguments. Overlap validation applies the same entity-name normalization and considers optional prefixed forms. Matching considers only current-location entities and carried, existing, visible objects. Hidden routes are excluded; visible blocked routes return their authored failure text.

Candidates rank by literal-token specificity, bound-entity specificity, scope (object/character, location, global), then author priority. Remaining ties show clarification and commit nothing. Conditions do not cause fallback to a broader action: the selected action returns its failed-requirement response. Reserved controls are recognized before authored actions; `look at` remains available as a vocabulary synonym.

When no candidate matches, `game.unknown_command_text` supplies the reply in both editor playtesting and the runner. Game settings exposes it as **Unknown command message**, using the usual formatted-message editor, validation, live variable/property expansion, reference management, and project search. Missing fields in older projects and bundles default to `I couldn't match that command. Try help, or use a visible object's name.` An explicitly empty message produces no reply. Unmatched commands retain their `unmatched` status and do not change state or fire command triggers; built-in controls, ambiguous commands, failed requirements, and completed-game replies keep their existing behavior. Content format remains 1 and player saves remain format 2.

One transaction buffers the entire resulting transcript and state. Effects run in authored order. Events run target-specific handlers, location/local handlers, then global handlers; within a scope, higher priority comes first, then stable trigger ID. Start and ending events notify all authored owners. Location entry/leave events also notify objects and characters present there. Mutation effects emit take/drop/open/close events only when applicable. Verb metadata supplies examination/use/speech and similar events without duplicating those mutation events.

Entry increments the visit count, fires first-entry handlers when applicable, then every-entry handlers, then describes the resulting location. `look` only describes. Ending terminates ordinary action processing, runs ending finalization once, displays the ending message, and displays an outcome line when one is set. Trigger dispatch is bounded to 2,048 operations and 64 nested events per transaction; failure rolls back both output and state.

Ending outcomes are optional: `victory`, `loss`, and `neutral` retain their existing meaning, while `null` or an omitted `outcome` means no classification. New endings default to no outcome. Writers serialize an unset outcome as explicit `null`, so older engines reject it rather than applying their old neutral default. Content format remains 1; games with unset outcomes require an engine supporting this nullable field. Existing explicit outcomes round trip unchanged. Validation still checks ending references and required-ending reachability. Completion is determined by `GameState.ending`, which stores the ending ID independently of its outcome. Autosaves and named saves remain in format 2, and restoring a completed game displays its message and any selected outcome without replaying ending handlers.

`Session::resume_messages` produces the title and either the current location description or completed ending as semantic spans. It resolves current saved variables/properties through the ordinary core message formatter, preserving colours, percent escaping, and literal substitutions. Live completion and resume share ending presentation. This read-only view runs no opening text, events, or effects and does not advance visits, hints, or response sequences. The terminal host only renders the returned spans and adds its loaded-slot notice.

Triggers add a default-empty `name` and default-null `watch` to the existing owner/event/priority/condition/effects model. A `TriggerWatch` stores a `ValueTarget` (global variable or entity property) and a `WatchMode` (`becomes_true`, the default, or `each_change`). Watches are excluded from ordinary event dispatch. Before a SET/arithmetic mutation, the engine captures matching watches and their conditions; after a real value change it captures eligible false-to-true transitions, or all matching conditions in `each_change` mode. Eligible watches run immediately in descending priority and stable ID order, rechecking their conditions before execution. Watches reference values directly and work regardless of their owner's location or visibility. Owner scope retains its existing meaning for event triggers.

Watch effects can cause nested value changes and ordinary events within the same transaction and recursion/operation limits. A failed watch rolls back the initiating command's state and transcript; END GAME stops remaining ordinary effects and finalizes once. Identical assignments do not fire, and watches do not run just because an initial value or restored save already satisfies their condition. No watch latch is persisted: comparing before/after conditions makes healing/rearming and save restoration consistent without changing save format 2. Older trigger files receive `name = ""` and `watch = null`; existing event behavior and block keys are retained. Older engines reject new trigger fields instead of silently ignoring watches. Validation checks watched references and accounts for watch effects in ending reachability without treating them as location-entry handlers.

Structural reachability follows routes and authored movement while excluding statically false conditions and branches. It cannot prove stateful puzzle solvability. The Locked Study walkthrough demonstrates an actual reachable ending.

`help <entity>` resolves a currently available object, character, or location using the ordinary name/alias and ignored-prefix matcher. Unknown or unavailable entities receive the same generic not-found response; ambiguous aliases request a more specific name. `game.help_mode` is `off`, `basic` (the default for new and older content), or `full`. Off retains general help and disables entity listings. Basic lists canonical verbs from authored actions owned by or referencing the requested entity, plus applicable route verbs, and prints generic syntax. It omits other entity names and does not filter verbs by puzzle requirements, priority, or other targets' presence, avoiding readiness signals. Its entity-name lookup still respects visibility and player scope.

Full help shares command candidate matching and ranking with execution. It lists a complete canonical phrase only if it selects one winning handler whose current requirements or route availability pass and which concerns the entity. Current-location listings include its available routes. Hidden, absent, remote, and character-held targets remain outside scope. A blocked higher-priority handler cannot expose a lower-priority fallback; tied winning handlers are omitted. Help runs no effects or triggers and leaves state/response cursors unchanged. After an ending it reports no authored commands available. Bare `help` retains general game help. The `help …` and `hint …` prefixes are reserved vocabulary. The playtest API accepts an optional `help_mode` override on session creation; this modifies only the session's project copy and is excluded from project saving/export.

### Response-sequence exhaustion

`respond` retains its stable `id`, ordered `responses`, `mode`, and `fallback` text. It adds `exhaustion` (`once`, the default, or `repeat`) and `on_exhausted: Vec<Effect>` (default empty for older content). Only `fallback` mode exhausts: the interaction after the final reply prints fallback text, then executes the follow-up effects in authored order. An empty fallback prints nothing. In `once` mode the effects run only on the first exhausted interaction; in `repeat` mode they run on every exhausted interaction. Fallback text prints every time independently. `repeat_last` and `loop` preserve their existing cursor semantics and never execute follow-ups; switching modes retains the authored follow-up blocks.

`GameState.sequences` continues to map sequence IDs to integer cursors. For a fallback sequence with N replies, N means all replies were printed and the first follow-up is pending. N+1 means its follow-up has run. N+1 is accepted only when that fallback sequence has follow-up effects; legacy fallback sequences without effects still stop at N. Marking N+1 before executing follow-ups prevents a nested trigger from re-entering a once-only flow. Effects share the command transaction and execution budget: a failure rolls back the cursor, all other changes, and output. STOP and END propagate through follow-ups to the enclosing action. Nested response sequences have independent IDs/cursors, and validation, state initialisation, reachability analysis, and editor text fields traverse their effect trees.

`reset_responses { sequence }` references an existing response-sequence ID and sets its cursor to zero, rearming once-only follow-ups. It resets only that sequence, without printing text or invoking an action/interaction event; nested sequences must be reset separately. A reset inside the selected sequence's own follow-up takes effect for its next invocation. A new session/playtest restart initialises every cursor. Loading a save restores cursors directly without replaying effects. The integer state representation is unchanged, so saves remain in format 2 and legacy cursors remain readable. Older binaries reject the new content fields/effect variant; older cursor validation also rejects N+1 rather than silently replaying a completed follow-up. Keep IDs stable, and publish a new content version when changing released sequences.

Blockly represents follow-ups as a statement input on RESPONSE SEQUENCE, with the once/repeat choice mirrored in the inspector. RESET RESPONSE SEQUENCE uses a project-wide dropdown of sequences, including nested ones; broken references remain visible for validation. Canonical effects determine the flow and saved workspaces must agree with them. Response and follow-up text edits preserve IDs and other effects.

### Authored puzzle hints

Locations, objects, and characters have `hints: Vec<HintSet>`, defaulting to empty for older content. Each set has a globally unique stable `id`, player-facing `name`, `available` condition, `solved` condition (default false), and ordered `stages`. Each `HintStage` has a globally unique stable `id`, editor `name`, applies-when `condition`, ordered nonempty text `clues`, and optional `solution`. All existing conditions apply; text uses the usual colour/placeholder validation and rendering. Empty stages/clues, broken references, or duplicate IDs are export/playtest errors. `game.hints_enabled` defaults true, independently of help mode; empty hint sets provide no assistance until authored.

`hint` lists only currently available entities with an applicable stage. `hint <entity>` selects the first available, unsolved set with a matching stage, then that set's first matching stage, in authored order. Each request reveals the next clue; exhausted clues repeat the last. A solution is never shown by ordinary hint requests: `hint <entity> solution` explicitly reveals it. Exact entity names/aliases take precedence over parsing a trailing `solution` modifier. An entity whose name ends in that word can request its answer by appending another `solution`. Unknown/ambiguous targets, disabled hints, inactive/solved puzzles, and ended playthroughs do not advance history.

`GameState.hints` is a sparse map from stage ID to `HintProgress { clues_seen, solution_seen }`. Only newly seen clues/solutions change it, causing normal autosave; repeating the final clue or an already seen solution leaves state unchanged. Stage changes preserve independent cursors. No gameplay effects, sequence advances, or command/interaction triggers run during hints. The `hint_used` condition references a hint-set ID and is true when any of its stages has seen a clue or solution; authors can use this in their own score/ending logic. The editor Hints tab edits the same canonical fields, and the test-state inspector displays/resets progress.

Hint authoring has synchronized Forms and Blockly views, a per-entity puzzle list, and a selection-based inspector for names, conditions, clues, and solutions. Each puzzle has a fixed-identity root with typed stage, clue, solution, and Boolean sockets. Only connected stages/clues contribute to canonical content; detached blocks remain editor drafts. Blockly layout is stored in `editor.blocks["hints:<puzzle-id>"]`, separately from action/trigger workspaces and excluded from exported content. Reconciliation applies form edits to the saved workspace by stable stage ID and matches existing clue blocks by text before reusing remaining blocks, preserving positions and drafts. Stage duplication creates independent, valid content IDs; undo/redo and reopening keep those IDs stable. Removing a solved condition block defaults to false, so an empty solved socket does not accidentally suppress the puzzle.

## Files and bundles

Saving compares a hash of managed project files and assets with the caller's disk revision. A mismatch returns HTTP 409 and leaves canonical files unchanged. Recovery drafts live under `.luna-recovery/`. Multi-file updates use a write-ahead journal and atomic per-file replacement; reopening completes an interrupted transaction only when current files still match its before/after contents. Conflicting external recovery edits are reported rather than overwritten. Project-local recovery and lock files are ignored by the generated Git ignore file.

The exported `.luna` is a standard deflated ZIP containing `manifest.json`, game/vocabulary/entity files, and declared assets under `assets/`. The manifest records format version, identity, content version, and SHA-256 hashes for the exact required file set. Export excludes `editor/`, recovery files, and player saves, and leaves the source project intact. Exported archives use file entries without separate directory entries.

Import checks checksums, required files, supported format, duplicate archive paths, safe relative paths, special files, and shared content validation. Resource ceilings are 64 MiB per file, 256 MiB per bundle/uncompressed content, and 10,000 ZIP entries. These are resource protections, not small authoring limits on responses or save slots.

Validated installation content is immutable. An atomic per-version JSON pointer selects a completed content generation, so failed replacement never exposes partial game data. Version locks prevent removal/replacement while that version is being played. Saves are stored separately and never deleted by replacement.

## Player persistence and rendering

Save-format v2 wraps the complete `GameState` including hint history, exact game identity/content version, a content fingerprint, UTC timestamps, and a label. The runner reads formats 1 and 2 and always writes 2; missing legacy hint history defaults to empty. A format-1 file carrying nonempty hint history is rejected as inconsistent. Older runners reject format 2 explicitly, preventing silent loss of progress. Saved hint stage IDs must exist, cursors must fit their clue lists, and seen solutions must still exist; incompatible edits produce a preserved-save error. Keep IDs stable and publish a new content version when changing released puzzle structure. Existing identity/fingerprint/schema checks remain in place.

Each slot uses atomic replacement. Named paths are derived from label hashes, and labels are never interpreted as paths. Loading restores state directly without start/entry events. Help and hint listing do not autosave; revealing a new clue or solution does. No hint effects are replayed on load.

The text parser produces plain spans with optional palette names. It rejects unknown, nested, mismatched, and unclosed tags and decodes literal escapes once. Browser rendering uses text nodes and CSS; terminal rendering alone introduces ANSI foreground sequences and resets each message. Plain rendering preserves text without tags. Assets and UI media are served locally.

Message formatting resolves `%variable_name%` and `%entity_id.property_name%` against current variables and custom properties after parsing colour markup. An exact global-variable name takes precedence; property lookup uses the longest matching entity ID when imported IDs contain dots. `%%` emits a literal percent sign. Text values retain the surrounding span colour and are inserted once without parsing their markup or placeholders. Validation checks the same references against initial schemas; missing references at runtime fail the transaction. The editor's insertion menu writes stable references into the message text. Preview fields show the authored placeholders, while playtesting shows their current values.
